# findex — Повнотекстовий пошуковий рушій

findex — це навчальний повнотекстовий пошуковий рушій, розроблений мовою Python у межах лабораторного практикуму. Проєкт реалізовано як повноцінний пакет із підтримкою суворої типізації, консольного інтерфейсу (CLI), алгоритмів ранжування BM25 та TF-IDF, а також комплексного тестового покриття.

---

## Етапи розробки та зміст лабораторних робіт

### Лабораторна робота №1: Токенізація, нормалізація та статистика корпусу
- Мета: реалізація базового конвеєра обробки тексту та статистичного аналізу.
- Ключові компоненти:
  - tokenizer.py: розбиття тексту на слова з підтримкою складних токенів (дефіси, апострофи). Забезпечено обов'язкову Unicode NFC-нормалізацію (unicodedata.normalize).
  - reader.py: потокове читання текстових документів корпусу з коректною обробкою кодувань.
  - stats.py: підрахунок загальної кількості слів, словника унікальних термів, середньої довжини документів та побудова топ-10 частотних термів.

### Лабораторна робота №2: Інвертований індекс та збереження стану
- Мета: створення масштабованої структури інвертованого індексу та механізму персистентності.
- Ключові компоненти:
  - models.py: датаклас Posting для збереження doc_id, частоти терма freq та точних списків позицій positions.
  - index.py: реалізація класу InvertedIndex з підтримкою протоколу Mapping (__getitem__, __len__, __iter__, __contains__).
  - Серіалізація стану індексу у бінарний формат (pickle) через методи save() та load().

### Лабораторна робота №3: Булеві запити, AST та ранжований пошук
- Мета: реалізація синтаксичного аналізу пошукових виразів та алгоритмів релевантності.
- Ключові компоненти:
  - query.py: побудова власного лексера (QueryLexer) та парсера рекурсивного спуску (QueryParser), що генерують дерево синтаксичного аналізу (AST) з підтримкою вузлів Term, Phrase, And, Or, Not та пріоритетів через дужки.
  - scoring.py: класи ранжування на базі формули Okapi BM25 (k1 = 1.5, b = 0.75) та зважування TF-IDF.
  - search.py: оцінка AST дерева (evaluate_ast), позиційний фразовий пошук за масивом індексів слів та фільтрація документів.

### Лабораторна робота №4: Пакетизація, CLI, тестування та суворий контроль якості
- Мета: перетворення кодової бази на продакшн-пакет із суворою типізацією та CLI.
- Ключові компоненти:
  - pyproject.toml: конфігурація пакування за стандартом PEP 517/621, налаштування залежностей, Ruff та Pyright.
  - cli.py: інтерфейс командного рядка на базі бібліотек typer та rich з командами index, search, stats, підтримкою експорту в JSON та візуалізацією таблиць.
  - utils.py: генерація контекстних текстових сніпетів із підсвічуванням збігів (extract_snippet) та декоратор заміру часу (timed).
  - Тестовий набір (tests/): понад 87% тестового покриття, використання pytest-cov, параметризованих тестів та property-based тестування (hypothesis).
  - Статичний аналіз: повна відповідність суворому режиму Pyright (typeCheckingMode = "strict" — 0 помилок) та форматування коду через Ruff.

## Встановлення та налаштування

1. Створення віртуального середовища:
   python3 -m venv .venv
   source .venv/bin/activate

2. Встановлення пакета з залежностями для розробки:
   pip install -e ".[dev]"

---

## Приклади використання CLI

1. Побудова індексу корпусу:
   findex index data/ -o index.bin

2. Перегляд метрик та статистики індексу:
   findex stats index.bin

3. Ранжований булевий пошук:
   - Пошук за логічним виразом із виводом сніпетів:
     findex search index.bin "python AND (fast OR simple) NOT legacy" -c data/ -k 5

   - Фразовий пошук із ранжуванням за метрикою TF-IDF:
     findex search index.bin '"inverted index"' --scorer tfidf

   - Експорт результатів у формат JSON:
     findex search index.bin "search AND engine" --json

## Лабораторна робота №5: Конкурентність і GIL (Паралельна індексація)

### Характеристики тестового стенду
- Процесор: Intel Core i5-10300H (4 фізичні ядра, 8 потоків)
- Операційна система: Ubuntu Linux (x86_64)
- Середовище: Python 3.12.13 (CPython з GIL) та перевірка концепції free-threaded Python 3.13t (`sys._is_gil_enabled() == False`)

### Архітектура паралельної індексації
- `build_partial(file_paths)`: функція верхнього рівня модуля, яка приймає шляхи до файлів чанка і будує локальний `InvertedIndex`.
- `merge_indices(indices)`: детерміновано зливає часткові індекси та сортує списки постингів.
- `run_parallel_indexing`: підтримує режими `serial`, `threads` (`ThreadPoolExecutor`) та `processes` (`ProcessPoolExecutor` із безпечним контекстом `spawn`).

### Reflection (Висновки та аналіз)
1. **Чому потоки під GIL не прискорили індексацію:**
   Токенізація регулярними виразами, нормалізація Unicode NFC та побудова словників позицій є задачами, обмеженими процесором (CPU-bound). У стандартному інтерпретаторі CPython глобальне блокування (GIL) дозволяє виконувати байткод лише одному потоку одночасно. Через конкуренцію за GIL (lock contention) і перемикання контексту `ThreadPoolExecutor` демонструє навіть незначне сповільнення (0.90x–0.96x).
2. **Чому процеси прискорили роботу і чим це оплачено:**
   `ProcessPoolExecutor` запускає окремі процеси з власним інтерпретатором та незалежним GIL, що дає змогу паралельно задіяти всі фізичні ядра процесора (прискорення до 3.61x). Ціна цього прискорення — зростання пікового споживання оперативної пам'яті (RSS), а також накладні витрати на міжпроцесну передачу даних (серіалізація та десеріалізація індексів через `pickle`).
3. **Закон Амдала та фаза злиття (`merge`):**
   Закон Амдала обмежує максимальне прискорення часткою послідовного коду: $S(N) = \frac{1}{(1 - P) + \frac{P}{N}}$. Злиття часткових індексів (`merge_indices`), створення процесів (`spawn`) та серіалізація `pickle` є послідовною частиною алгоритму, через яку крива прискорення відхиляється від ідеальної лінійної прямої при збільшенні кількості воркерів до 8.
4. **Поведінка на збірці Python 3.13t без GIL:**
   При відключеному GIL (`sys._is_gil_enabled() == False`) потоки у `ThreadPoolExecutor` виконуються на різних ядрах справді паралельно без накладних витрат на `pickle` та дублювання пам'яті процесів, проте вимагають потокобезпечної синхронізації при доступі до спільних мутабельних структур даних.
