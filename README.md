# Лабораторна робота 1: Ітератори, генератори та корпус текстів (findex)

## Опис проєкту
Проєкт реалізує початковий етап пошукової системи **findex** — конвеєр обробки текстових документів. Обробка побудована на лінивих ітераторах та генераторах (`yield`), що дозволяє обробляти великі обсяги даних із мінімальним використанням оперативної пам'яті.

## Структура
- `src/findex/reader.py` — генератор `iter_documents()`, що ліниво зчитує файли корпусу через `pathlib`.
- `src/findex/tokenizer.py` — генератор `tokenize()`, що виконує Unicode-нормалізацію (NFC), переведення в нижній регістр і враховує слова з дефісами, апострофами та числа.
- `src/findex/stats.py` — модуль збору статистики (однопрохідний лінивий та жадібний підходи) з профілюванням через `tracemalloc`.
- `tests/test_tokenizer.py` — юніт-тести токенізатора на базі `pytest`.

## Порівняння продуктивності (Streaming vs Eager)

Вимірювання проводилися на корпусі з 274 документів (485 814 токенів, унікальний словник: 25 010 слів).

| Режим | Час виконання (с) | Пікова пам'ять (МБ) |
| :--- | :---: | :---: |
| **Streaming (Генератори)** | ~1.541 | **2.48** |
| **Eager (Списки)** | ~0.760 | **31.18** |

### Пояснення різниці пам'яті
1. **Куди пішла пам'ять у версії Eager:**
   - Створення єдиного списку всіх зчитаних файлів (`raw_texts`).
   - Створення масивного списку з 485 тисяч об'єктів рядків (`all_tokens`) одночасно в оперативній пам'яті перед передачею в `Counter`.
2. **Чому Streaming настільки ефективний:**
   - Пам'ять практично не зростає зі збільшенням розміру корпусу.
   - Одночасно в пам'яті знаходиться лише поточний файл і поточне слово.
   - Основний обсяг пам'яті (2.48 МБ) витрачається виключно на збереження словника унікальних термінів (`Counter`), який є спільним для обох підходів.

## Лабораторна робота 2: Інвертований індекс та булевий пошук

### 1. Характеристики побудованого індексу
- **Корпус:** 274 документи
- **Унікальних термінів у словнику:** 25 010
- **Час індексації в один прохід:** 0.68 с
- **Оптимізація пам'яті:** використання `@dataclass(slots=True)` для `DocMeta` та `Posting`, що прибирає накладні витрати `__dict__` для сотень тисяч об'єктів.

### 2. Бенчмарк: Merge Postings vs Set Intersection
Порівняння швидкості виконання запиту `time AND day` (знайдено 166 документів):

| Метод перетину | Алгоритм | Час пошуку |
|---|---|---|
| **Merge Postings** | Two-Pointer лінійне злиття відсортованих списків ($O(L_1 + L_2)$) | **0.210 мс** |
| **Set Intersection** | Перетворення в хеш-множини Python (`set & set`) | **0.506 мс** |

**Висновки:**
1. Алгоритм злиття двох вказівників (`merge`) виявився швидшим приблизно у 2.4 раза, оскільки працює безпосередньо по вже впорядкованих списках `doc_id` без створення проміжних хеш-таблиць у пам'яті.
2. Перед перетином застосовано евристику сортування термінів за довжиною postings list (`doc_lists.sort(key=len)`), що мінімізує кількість операцій порівняння.

### 3. Безпека десеріалізації (pickle)
Функція `pickle.load()` є потенційно небезпечною при завантаженні файлів з неперевірених джерел, оскільки протокол pickle дозволяє виконувати довільний код через метод `__reduce__` прямо під час відновлення об'єкта (Remote Code Execution).
